CASE 1: Full Match (Incoming + Resting Both Complete)

📌 Scenario

BUY 5 NVDA @ 120.00 incoming meets SELL 5 NVDA @ 120.00 resting

⚙️ Execution Flow

PRE-STATE:
Orders Table:
┌─────────┬────────┬──────────┬────────┬──────────┐
│order_id │ side   │ quantity │ filled │ status   │
├─────────┼────────┼──────────┼────────┼──────────┤
│ R1-UUID │ SELL   │ 5        │ 0      │ NEW      │
│ I1-UUID │ BUY    │ 5        │ 0      │ NEW      │
└─────────┴────────┴──────────┴────────┴──────────┘

Kafka In:
→ ORDER_PLACED (I1: BUY 5 NVDA @ 120.00)

Step-by-Step Execution

  • Query for resting opposite: 
    SQL: SELECT * FROM orders
WHERE instrument_id = NVDA_ID
  AND side = 'SELL'
  AND status IN ('NEW', 'PARTIALLY_FILLED')
  AND limit_price <= 120.00
  AND order_id != 'I1-UUID'
ORDER BY limit_price DESC, created_at ASC

RESULT: [R1 {quantity: 5, filled_quantity: 0}]
  • Calculate match: 
    remaining = 5 (I1 wants 5)
restingRemaining = 5 (R1 has 5)
matchQuantity = min(5, 5) = 5
executionPrice = 120.00 (resting's limit price)
restingNewStatus = "FILLED" (0 + 5 >= 5)
  • Re-check resting account: 
    Does Account-1 still have 5 NVDA shares?
SQL: SELECT held_quantity FROM positions_view
     WHERE account = Acc-1 AND instrument = NVDA
RESULT: 5 shares ✓
  • Settlement (SettlementService.settleMatch): 
    @Transactional BEGIN

Guard 1 - Update resting order:
SQL: UPDATE orders
     SET filled_quantity = 5,
         status = 'FILLED',
         executed_price = 120.00,
         fee_amount = 2.50
     WHERE order_id = 'R1-UUID'
       AND filled_quantity = 0
RESULT: 1 row affected ✓

Guard 2 - Insert trade records (both sides):
SQL: INSERT INTO trades (order_id, executed_price, quantity, created_at)
     VALUES ('R1-UUID', 120.00, 5, NOW())

SQL: INSERT INTO trades (order_id, executed_price, quantity, created_at)
     VALUES ('I1-UUID', 120.00, 5, NOW())

Guard 3 - Update Account-1 balance:
newBalance = 1000.00 + 597.50 (5 × 120.00 - fee)
SQL: UPDATE accounts
     SET cash_balance = 1597.50, version = 2
     WHERE id = 1 AND version = 1
RESULT: 1 row affected ✓

Guard 4 - Update Account-2 balance:
newBalance = 650.00 - 627.50 (5 × 120.00 + fee)
SQL: UPDATE accounts
     SET cash_balance = 22.50, version = 6
     WHERE id = 2 AND version = 5
RESULT: 1 row affected ✓

@Transactional COMMIT ✓
  • Finalize incoming order: 
    SQL: UPDATE orders
     SET filled_quantity = 5,
         status = 'FILLED',
         fee_amount = 2.75
     WHERE order_id = 'I1-UUID' AND status = 'NEW'
RESULT: 1 row affected ✓

📊 POST-STATE

Orders Table:
┌─────────┬────────┬──────────┬────────┬──────────┐
│order_id │ side   │ quantity │ filled │ status   │
├─────────┼────────┼──────────┼────────┼──────────┤
│ R1-UUID │ SELL   │ 5        │ 5      │ FILLED   │
│ I1-UUID │ BUY    │ 5        │ 5      │ FILLED   │
└─────────┴────────┴──────────┴────────┴──────────┘

Trades Table (NEW):
┌───────────┬──────────┬────────────────┬──────────┐
│trade_id   │order_id  │executed_price  │quantity  │
├───────────┼──────────┼────────────────┼──────────┤
│ T1-UUID   │ R1-UUID  │ 120.00         │ 5        │
│ T2-UUID   │ I1-UUID  │ 120.00         │ 5        │
└───────────┴──────────┴────────────────┴──────────┘

Kafka Out:
← ORDER_FILLED (R1): {orderId: R1, status: FILLED, filledQty: 5}
← ORDER_FILLED (I1): {orderId: I1, status: FILLED, filledQty: 5}

CASE 2: Partial Match (Incoming Still Wants More)

📌 Scenario

BUY 10 NVDA @ 120.00 incoming meets SELL 5 NVDA @ 120.00 resting

⚙️ Execution Flow

Loop Iteration 1:
─────────────────
matchQuantity = min(10, 5) = 5
executionPrice = 120.00
restingNewStatus = "FILLED" (0 + 5 >= 5)

SettlementService.settleMatch():
SQL: UPDATE orders SET filled_quantity = 5, status = 'FILLED'
     WHERE order_id = 'R1-UUID' AND filled_quantity = 0
Result: 1 row affected ✓

INSERT 2 trades (R1, I1)
Update both account balances ✓
Publish: ORDER_FILLED(R1) to Kafka

Update counters:
remaining = 10 - 5 = 5  ← I1 STILL WANTS 5 MORE!
totalMatched = 5
progressedThisPass = true

Loop Iteration 2:
─────────────────
while (remaining > 0) → 5 > 0 → TRUE ✓
Back to query for more resting orders

SCENARIO A: No more resting orders
  candidates = []
  Break from loop
  remaining = 5 (I1 still has 5 qty unmatched)

SCENARIO B: Another resting order found (R2)
  Repeat match process with R2...

📊 POST-STATE (if no more resting)

Orders Table:
┌─────────┬────────┬──────────┬────────┬─────────────────┐
│order_id │ side   │ quantity │ filled │ status          │
├─────────┼────────┼──────────┼────────┼─────────────────┤
│ R1-UUID │ SELL   │ 5        │ 5      │ FILLED          │
│ I1-UUID │ BUY    │ 10       │ 5      │ PARTIALLY_FILLED│
└─────────┴────────┴──────────┴────────┴─────────────────┘

Trades Table (NEW):
┌───────────┬──────────┬────────────────┬──────────┐
│trade_id   │order_id  │executed_price  │quantity  │
├───────────┼──────────┼────────────────┼──────────┤
│ T1-UUID   │ R1-UUID  │ 120.00         │ 5        │
│ T2-UUID   │ I1-UUID  │ 120.00         │ 5        │
└───────────┴──────────┴────────────────┴──────────┘

Kafka Out:
← ORDER_FILLED (R1): {orderId: R1, status: FILLED, filledQty: 5}
← ORDER_PARTIALLY_FILLED (I1): {orderId: I1, status: PARTIALLY_FILLED, filledQty: 5, totalQty: 10}

⏳ I1 now RESTS on order book with 5 qty remaining!

CASE 3: Multiple Matches (Split Across Multiple Resting Orders)

📌 Scenario

BUY 10 NVDA @ 120.50 incoming meets TWO resting SELL orders

⚙️ Execution Flow

PRE-STATE:
┌─────────┬────────┬──────────┬────────┬──────────┐
│ R1-UUID │ SELL   │ 3        │ 0      │ NEW      │ price: 119.50
│ R2-UUID │ SELL   │ 7        │ 0      │ NEW      │ price: 120.00
│ I1-UUID │ BUY    │ 10       │ 0      │ NEW      │ limit: 120.50
└─────────┴────────┴──────────┴────────┴──────────┘

Loop Iteration 1:
─────────────────
Query: ... WHERE limit_price <= 120.50 ORDER BY limit_price DESC, created_at ASC
RESULT: [R2 {qty: 7, price: 120.00}, R1 {qty: 3, price: 119.50}]
(R2 first due to price-then-time priority)

Process R2:
  matchQuantity = min(10, 7) = 7
  executionPrice = 120.00
  restingNewStatus = "FILLED"
  SettleMatch() → R2 FILLED
  remaining = 10 - 7 = 3

Process R1:
  matchQuantity = min(3, 3) = 3
  executionPrice = 119.50
  restingNewStatus = "FILLED"
  SettleMatch() → R1 FILLED
  remaining = 3 - 3 = 0

Loop Iteration 2:
─────────────────
while (remaining > 0) → 0 > 0 → FALSE
Exit while loop

📊 POST-STATE

Orders Table:
┌─────────┬────────┬──────────┬────────┬──────────┐
│ R1-UUID │ SELL   │ 3        │ 3      │ FILLED   │
│ R2-UUID │ SELL   │ 7        │ 7      │ FILLED   │
│ I1-UUID │ BUY    │ 10       │ 10     │ FILLED   │
└─────────┴────────┴──────────┴────────┴──────────┘

Trades Table (4 NEW records):
┌───────────┬──────────┬────────────────┬──────────┐
│ T1-UUID   │ R2-UUID  │ 120.00         │ 7        │ (1st match)
│ T2-UUID   │ I1-UUID  │ 120.00         │ 7        │ (1st match)
│ T3-UUID   │ R1-UUID  │ 119.50         │ 3        │ (2nd match)
│ T4-UUID   │ I1-UUID  │ 119.50         │ 3        │ (2nd match)
└───────────┴──────────┴────────────────┴──────────┘

Kafka Out (4 events):
← ORDER_FILLED(R2): {orderId: R2, status: FILLED, filledQty: 7, avgPrice: 120.00}
← ORDER_FILLED(R1): {orderId: R1, status: FILLED, filledQty: 3, avgPrice: 119.50}
← ORDER_FILLED(I1): {orderId: I1, status: FILLED, filledQty: 10, avgPrice: 119.70}

💰 Account-1 (I1 buyer):
  Paid: (7 × 120.00) + (3 × 119.50) + fees = 1297.50

CASE 4: Partial Resting Order (Resting Has More Qty)

📌 Scenario

BUY 3 NVDA @ 120.00 incoming meets SELL 5 NVDA @ 120.00 resting

⚙️ Execution Flow

Calculate match:
  remaining = 3
  restingRemaining = 5
  matchQuantity = min(3, 5) = 3

Determine resting new status:
  filled + match = 0 + 3 = 3
  3 < 5 (total qty)
  restingNewStatus = "PARTIALLY_FILLED"  ← Different!

SettlementService.settleMatch():
  SQL: UPDATE orders
       SET filled_quantity = 0 + 3 = 3,
           status = 'PARTIALLY_FILLED',  ← PARTIALLY_FILLED!
           executed_price = 120.00
       WHERE order_id = 'R1-UUID' AND filled_quantity = 0

  Result: 1 row affected ✓

  INSERT 2 trades (R1, I1)
  Update both account balances ✓

  Publish: ORDER_PARTIALLY_FILLED(R1) to Kafka  ← Different event!

📊 POST-STATE

Orders Table:
┌─────────┬────────┬──────────┬────────┬─────────────────┐
│ R1-UUID │ SELL   │ 5        │ 3      │ PARTIALLY_FILLED│
│ I1-UUID │ BUY    │ 3        │ 3      │ FILLED          │
└─────────┴────────┴──────────┴────────┴─────────────────┘

Trades Table (NEW):
┌───────────┬──────────┬────────────────┬──────────┐
│ T1-UUID   │ R1-UUID  │ 120.00         │ 3        │
│ T2-UUID   │ I1-UUID  │ 120.00         │ 3        │
└───────────┴──────────┴────────────────┴──────────┘

Kafka Out:
← ORDER_PARTIALLY_FILLED(R1): {orderId: R1, status: PARTIALLY_FILLED, filledQty: 3, remainingQty: 2}
← ORDER_FILLED(I1): {orderId: I1, status: FILLED, filledQty: 3}

⏳ R1 CONTINUES RESTING with 2 qty waiting for next counterparty!

CASE 5: No Resting Orders (Silent Rest)

📌 Scenario

BUY 5 NVDA @ 120.00 incoming, but NO SELL orders on book

⚙️ Execution Flow

Step 1: Query for resting
  SQL: SELECT * FROM orders
       WHERE instrument_id = NVDA_ID
         AND side = 'SELL'
         AND status IN ('NEW', 'PARTIALLY_FILLED')
         AND limit_price <= 120.00

  RESULT: [] (empty - no resting SELL orders)

Step 2: Check if empty
  if (candidates.isEmpty()) {
    break;  ← Exit immediately!
  }

Step 3: Return from match()
  return Result(totalMatched=0, lastExecutionPrice=null, totalFee=0)

Step 4: Back in OrderExecutionService
  if (result.matchedAnything()) → 0 > 0 → FALSE

  NO finalizeIncomingOrder() called!
  NO events published!

📊 POST-STATE

Orders Table:
┌─────────┬────────┬──────────┬────────┬──────────┐
│ I1-UUID │ BUY    │ 5        │ 0      │ NEW      │ ← Silent rest!
└─────────┴────────┴──────────┴────────┴──────────┘

Trades Table: (No new trades)

Kafka Out: (No events published!)

⏳ I1 now RESTS silently on the order book
   Client learns about this only by:
   1. Polling GET /accounts/{id}/orders
   2. Receiving ORDER_EXPIRED event (after 30 mins, Phase 3)
📝 Note: This is intentional design. No counterparty means the order just waits. The client doesn't get an event notification because nothing happened yet - the order is just sitting on the book.

CASE 6: Concurrent Contention (Race Condition)

📌 Scenario

TWO incoming orders (I1, I2) simultaneously try to match the SAME resting order R1

⚙️ Execution Flow

PRE-STATE:
┌─────────┬────────┬──────────┬────────┬──────────┐
│ R1-UUID │ SELL   │ 10       │ 0      │ NEW      │
│ I1-UUID │ BUY    │ 5        │ 0      │ NEW      │
│ I2-UUID │ BUY    │ 6        │ 0      │ NEW      │
└─────────┴────────┴──────────┴────────┴──────────┘

═══════════════════════════════════════════════════════

THREAD 1 (processing I1) - Commits FIRST:
─────────────────────────────────────────
Query: candidates = [R1 {qty: 10, filled: 0}]
Calculate: matchQuantity = 5
Settle: UPDATE orders SET filled_quantity = 5
        WHERE order_id = 'R1-UUID' AND filled_quantity = 0
Result: 1 row affected ✓
COMMIT
→ R1 now: filled_qty = 5, status = PARTIALLY_FILLED

═══════════════════════════════════════════════════════

THREAD 2 (processing I2) - Starts AFTER Thread 1:
──────────────────────────────────────────────────
Query: SELECT ... FROM orders WHERE order_id = 'R1-UUID'
Result: R1 {qty: 10, filled: 5, status: PARTIALLY_FILLED}
        (filled_quantity changed from 0 to 5!)

Calculate: restingRemaining = 10 - 5 = 5 (recalculated!)
           matchQuantity = min(6, 5) = 5

Settle: UPDATE orders
        SET filled_quantity = 5 + 5 = 10,
            status = 'FILLED'
        WHERE order_id = 'R1-UUID' AND filled_quantity = 5  ← KEY!
Result: 1 row affected ✓ (WHERE clause matched)
COMMIT
→ R1 now: filled_qty = 10, status = FILLED

═══════════════════════════════════════════════════════

SCENARIO: If Thread 2 runs BEFORE Thread 1:
────────────────────────────────────────────
THREAD 2 (runs first):
  UPDATE ... SET filled_quantity = 5
  WHERE filled_quantity = 0
  Result: 1 row affected ✓

THREAD 1 (runs second):
  UPDATE ... SET filled_quantity = 5
  WHERE filled_quantity = 0  ← WHERE doesn't match anymore!
  Result: 0 rows affected ❌

  if (rows == 0) {
    return MatchOutcome.contended();  ← Contention detected!
  }

  Log: "Resting order R1 was matched by concurrent delivery first"
  continue;  ← Skip to next candidate

  I1 may partially match or rest waiting
⚠️ Race Condition Handling: The optimistic lock (Guard 1) on filled_quantity ensures correctness. If two threads try to update the same resting order, only ONE succeeds, and the other gets MatchOutcome.contended() and retries with the next candidate. No data corruption occurs.

CASE 7: Affordability Failure (Account Can't Afford Re-Check)

📌 Scenario

Resting order placed, but account balance now insufficient when incoming arrives

Between R1 placement and I1 arrival: Resting account withdrew $950, leaving only $50 (not enough for $1200 purchase).

⚙️ Execution Flow

Step 1: Query resting
  candidates = [R1]

Step 2: Calculate match
  matchQuantity = 10

Step 3: Re-check resting account affordability
  SQL: SELECT cash_balance, version FROM accounts
       WHERE id = Resting_ID
  Result: {cash_balance: 50.00, version: 10}

  needToPay = 10 × 120 + fee = $1200
  50.00 < 1200.00 ❌

  ExecutionRuleCheck.checkAffordable()
    → returns Optional.of(INSUFFICIENT_FUNDS)

Step 4: Handle failure
  if (restingCheck.isPresent()) {
    log.info("Resting order {} can no longer be honoured (INSUFFICIENT_FUNDS) - skipping", R1);
    continue;  ← Skip this resting order, try next!
  }

  ❌ R1 is SKIPPED
  No settleMatch() called
  No update to R1
  No Kafka events

Step 5: Try next resting order
  Loop continues to find next candidate
  (or exits if no more)

📊 POST-STATE

Orders Table: (UNCHANGED)
┌─────────┬────────┬──────────┬────────┬──────────┐
│ R1-UUID │ BUY    │ 10       │ 0      │ NEW      │ ← Still waiting!
│ I1-UUID │ SELL   │ 10       │ 0      │ NEW      │ ← Still waiting!
└─────────┴────────┴──────────┴────────┴──────────┘

Kafka Out: (No events)

Both orders remain resting on the book, waiting for future opportunities
or for the resting account to deposit more cash.
⚠️ Design Point: This is a rare but real scenario. The resting order WAS valid when placed (had sufficient funds), but circumstances changed. Rather than reject it retroactively, the system gracefully skips it and tries the next counterparty. The order remains "NEW" until either:
  • Account deposits more cash and another incoming order crosses it
  • Order is cancelled by the owner
  • Order expires (Phase 3 feature)

🔑 Key Insights

The Two Guards in SettleMatch()

Guard 1 (Conditional Status Update): Uses optimistic lock on filled_quantity to ensure only ONE thread updates a resting order per match. Prevents race conditions.

Guard 2 (Version Lock on Accounts): Uses optimistic lock on Accounts.version to handle concurrent balance updates. Retried up to 3 times with exponential backoff.

Why Trades Table Has 2 Rows Per Match

Each match creates TWO trade records (one per side) because:

  • Portfolio Visibility: Both accounts need to see their fill via Trades table
  • Audit Trail: Complete record of who traded with whom
  • Fee Tracking: Each side may pay different fees in their own currency

Price-Time Priority

Resting orders are matched by:

  1. Price Priority: Best price first (highest for SELLs, lowest for BUYs)
  2. Time Priority: Within same price, oldest order first (FIFO)
  3. Execution Price: Always the resting order's limit price (price improvement for incoming)

Silent Rest (Case 5)

When an order rests with NO matching event, the client only learns about it through:

  • Polling: GET /accounts/{id}/orders
  • Future fill: When counterparty arrives and fills it
  • Expiration: ORDER_EXPIRED event after TTL (Phase 3)

This is intentional - no event = nothing happened.
